之后会怎样 / 怎么恢复
  • 单个 hook 失败不影响其他 hook（非 blocking 错误只产生 stderr 消息）

考据注记（源码实读 · claude-code 仓库）
  1. src/hooks/ 不是 hook 系统——里面是约 90 个 React UI hooks（useCanUseTool 等）；生命周期 hook 引擎真正在 src/utils/hooks.ts（5190 行）+ 配置侧 src/utils/hooks/ + 触发侧 src/services/tools/toolHooks.ts / toolExecution.ts。工具点三个事件的真实位置：PreToolUse toolExecution.ts:842、PostToolUse :1472/:1558、PostToolUseFailure :1782。
  2. 27 个事件的常量表有两份一模一样的定义：agentSdkTypes.js:4-32 与 sdk/coreTypes.ts:25-53（改一处不改另一处会失同步——证据 JSON 同款存疑）。其余事件的触发点：UserPromptSubmit processUserInput.ts:190（blocking 会擦掉用户原输入）、SessionStart sessionStart.ts:132、Stop query/stopHooks.ts:189。
  3. 配置合并优先级有张力：hooks.ts:1852-1854 注释说 Map 去重「last entry wins（最后合并的 scope 胜出）」，而 hooksSettings.ts sortMatchersByPriority 又按 user/project/local 排展示优先级、plugin/builtin 垫底（999）——冲突场景的实际胜者未逐条追踪，本图如实按「五源合并 + 去重」呈现。
  4. hook 的 allow 不等于免检：resolveHookPermissionDecision（toolHooks.ts:330-344 注释）明说 hook allow 不绕过 settings 的 deny/ask 规则，仍要跑 checkRuleBasedPermissions。
  5. 信任门是安全底线：交互模式下所有 hook 都要求工作区信任（hooks.ts:287-297 shouldSkipHookDueToTrust，注释点名历史漏洞：SessionEnd/SubagentStop 曾在信任前执行）。
  6. 可部分生效的写点：PreToolUse 的 updatedInput 在 passthrough 时立即覆写 processedInput（toolExecution.ts:876-880）——即使之后权限被拒，新 input 已经生效、但工具没执行。
