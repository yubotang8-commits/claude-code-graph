Provider 选择与客户端构造分发

组件 06-providers-compat · 多厂商接入

一次模型请求怎么决定走哪家 API：用户配置（/provider、/login）落到两条通道 → 每次请求用纯函数判定 → 第三方走适配层、Anthropic 系走 SDK 客户端工厂 → 凭据与请求头就位后交给重试层发流式请求。共 7 条通路。

深入细节（证据与考据）
  • 证据来源：src/utils/model/providers.ts（getAPIProvider 纯函数与优先级）、src/utils/model/providerClassification.ts（7 个 APIProvider 枚举）、src/services/api/claude.ts:1343-1381（适配层分流三检查）、src/services/api/client.ts:84-316（getAnthropicClient 四分支）、client.ts:356-389（buildFetch）、src/commands/provider.ts:126-161（/provider 写入语义）、src/components/ConsoleOAuthFlow.tsx:880-918（/login 写 modelType 并清客户端缓存）、src/services/api/openai/client.ts、grok/client.ts、gemini/client.ts（各适配层客户端）。
  • 判定优先级原文：modelType 只匹配 openai/gemini/grok（providers.ts:16-18）→ CLAUDE_CODE_USE_BEDROCK/VERTEX/FOUNDRY（:20-22）→ CLAUDE_CODE_USE_OPENAI/GEMINI/GROK（:24-26）→ 默认 firstParty。即 settings 里选了 openai 会压过 env 里的云厂商通道；而 bedrock/vertex/foundry 永远只有 env 通道（/provider 对云厂商不写 settings.json，provider.ts:148-156）。
  • 「无效构造的坑」：getAPIProvider()==='openai' 走 modelType 路径而 CLAUDE_CODE_USE_OPENAI 未设时，getAnthropicClient 的调用点（如 verifyApiKey、buildFetch 内部检查）仍会构造一个 firstParty Anthropic 客户端——该实例在 openai 路径不会被用于发请求，属无效构造。
  • buildFetch 细节：包装发生在云分支判定之前，四个 Anthropic 系客户端共用；但 x-client-request-id 仅在 getAPIProvider()==='firstParty' 且 ANTHROPIC_BASE_URL 指向官方域名（或未设）时注入（client.ts:366-376），用于超时场景下与服务器日志对账。ANTHROPIC_BASE_URL 配了第三方地址时被视为非官方（providers.ts:40-56）。
  • 客户端缓存差异：firstParty 侧每次调用都重建 Anthropic 实例；openai/grok 有模块级 cachedClient 单例，/login 改完 OPENAI_* 环境变量后靠显式 clearOpenAIClientCache 失效（ConsoleOAuthFlow.tsx:917），否则沿用旧配置。gemini 无客户端对象，直接每次手写 fetch。
  • 考据注记（api-streaming.json uncertainties）：Bedrock/Vertex/Foundry 三条云 SDK 分支只核验到构造参数（区域解析、凭据刷新、skipAuth/Bearer），SDK 实体在 @anthropic-ai/vertex-sdk / foundry-sdk 等包内未逐行核验；Vertex 分支每次新建 GoogleAuth 实例（client.ts:232-239 TODO 注释自述），靠 projectId 兜底防 GCP 外 12 秒元数据超时。
  • 7 路全景：firstParty（默认直连）、bedrock（AWS）、vertex（Google Cloud）、foundry（Azure）走 Anthropic SDK 家族四分支；openai、gemini、grok 走三个独立适配层（后两者细节见同目录 openai-adapter.html 流程图）。
