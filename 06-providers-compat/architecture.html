组件架构：模型服务路由与兼容层

06-providers-compat · 组成模块与调用关系

一次模型调用怎么发往七种后端：主循环发起 → 核心生成器先做共用预处理再组装请求 → 路由判定按配置七选一——官方通路交给客户端工厂按「直连 / 云托管」四分支构造，三家兼容层把别家格式转成自家格式、回复流也转回自家事件；重试与观测全程护航；底部规范化桥是「输出同构、下游零改动」的落点。

  • 分流点：claude.ts:1343（OpenAI）/ 1358（Gemini）/ 1371（Grok），位于共用预处理（消息规范化 claude.ts:1289）之后、Anthropic 专有逻辑（功能头组装 1102、系统提示 1433、缓存断点）之前；主入口 queryModel（claude.ts:1048），上游经 src/query/deps.ts:35 的 callModel 接入主循环。
  • 路由判定：providers.ts:12-29——settings.modelType（仅识别 openai/gemini/grok 三值）优先，其次 CLAUDE_CODE_USE_BEDROCK/VERTEX/FOUNDRY，再次 CLAUDE_CODE_USE_OPENAI/GEMINI/GROK，默认 firstParty；七值类型定义见 providerClassification.ts:1-8。
  • 官方客户端工厂：client.ts:84-316——bedrock 分支 153-190（AWS 凭据/Bearer token）、foundry 191-220（Azure AD 或 API key）、vertex 221-298（GoogleAuth+区域解析）、默认直连 301-315（OAuth 或 API key）；请求 ID 包装 356-389；bedrockClient.ts 为薄包装。
  • 「下游不改」的直接证据：openai/index.ts:214-219 自述把 Anthropic 格式消息/工具转为 OpenAI 格式、把回复流转回内部事件供既有查询管线消费；Grok 复用同一流适配器（grok/index.ts:121-124）；Gemini 走原生接口（gemini/index.ts:117 起适配）。转换器与流适配器实现在 packages/@ant/model-provider/src/。
  • 重试：withRetry.ts:170-517（默认 10 次指数退避+抖动、连续 3 次过载触发模型回退、上下文超限自动下调输出上限）；错误翻译在 errors.ts / errorUtils.ts。
  • 配置入口：commands/provider.ts:88/104/118 写 modelType（openai/grok/gemini）、:143 通用写入，bedrock/vertex/foundry 仅设环境变量（:126-156）；/login 表单 ConsoleOAuthFlow.tsx:461/488 提供选项、:888 等处写 modelType。
  • 考据注记：本组件完整组成 12 个模块，本图并为 10 盒——错误翻译（api-error-mapping）并入「重试与错误翻译」；实验功能头组装（betas-assembly，claude.ts:1102 调用，按模型能力开启长上下文/交错思维链等）省略未画；「观测与记账」合并了日志、缓存命中检测、Langfuse 对接、VCR 录制回放四个文件。
  • 考据注记：Grok 没有 /login 表单入口（ConsoleOAuthFlow.tsx 全文检索 grok 为 0 命中，本次复核确认），只能经 /provider 命令或环境变量启用——与仓库自述文档「通过 /login 配置」的说法有出入；/login 实际持久化 settings.modelType（优先级高于 CLAUDE_CODE_USE_* 环境变量），两者是覆盖关系而非并列。
  • 考据注记：bedrock/vertex/foundry 三条云分支无法经 settings.modelType 设置；其 SDK 内部行为未逐行核验（实现在依赖包内，本环境不装依赖、只读源码）。
  • 考据注记：路由判定也被客户端工厂（client.ts:367）、功能头组装、重试与遥测多方调用，图上只画了核心生成器的主调用；三兼容层各自调用「观测与记账」与底部规范化桥（OpenAI 层复做预处理见 openai/index.ts:235-293），为避免连线拥挤未画。配置入口→路由判定的箭头表示「写入其读取的配置」，非函数调用。
  • 延伸：单次流式请求的事件全程见组件 05；重试与模型回退的完整链路见组件 07。
