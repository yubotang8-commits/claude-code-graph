06-providers-compat · openai-adapter

后端不是 Anthropic 而是 OpenAI 兼容端点（vLLM / DeepSeek / Ollama，或 ChatGPT 订阅）时的一次模型调用：请求先被翻译成 OpenAI 格式发出，对方回的 SSE 增量流再被逐块翻译回 Anthropic 自家事件——主循环和下游全程无感，以为什么都没变。

深入细节（证据与考据）
  • 证据来源：src/services/api/claude.ts:1343-1356（openai 分流与动态 import）、src/services/api/openai/index.ts:220-580（queryModelOpenAI 全流程：模型映射 232、复做预处理 235-293、格式转换 306-312、后端选择 373-409、事件循环 428-535、组装 490-526、Langfuse 537-554、安全兜底 557-569、catch 570-580）、packages/@ant/model-provider/src/shared/openaiStreamAdapter.ts:36-356（状态机与 finish_reason 映射）、packages/@ant/model-provider/src/providers/openai/modelMapping.ts:36-55（模型映射优先级）。
  • 与 Anthropic 路径的关键差异：官方路径每个 content_block_stop 就组装一条 AssistantMessage 逐块产出；OpenAI 路径把组装推迟到 message_stop 一次性完成（代码注释明言 matching the Anthropic SDK path），中断时已收到的块靠循环外安全兜底补组装。
  • 无重试：OpenAI 客户端显式 maxRetries:0，任何错误只转成一条错误 AssistantMessage；Anthropic 路径的 withRetry 十次指数退避不覆盖此通路。
  • max_tokens 必须显式传：多数兼容端点默认值极小，思考模式会先吃光预算（openai/index.ts:331-347 注释）；这里用 64000 上限而非官方路径的 8k 槽位上限，因为 OpenAI 路径没有对应的自动升档重试。
  • 模型映射优先级：OPENAI_MODEL > OPENAI_DEFAULT_{FAMILY}_MODEL > ANTHROPIC_DEFAULT_{FAMILY}_MODEL > DEFAULT_MODEL_MAP（sonnet→gpt-4o、opus→o3、haiku→gpt-4o-mini）> 原名透传。
  • DeepSeek 细节：空 reasoning_content 也必须开 thinking 块并在后续请求回传，否则对方 400（openaiStreamAdapter.ts:133-137 注释）。
  • usage 映射（openaiStreamAdapter.ts:16-24 注释）：prompt_tokens−cached−cache_write→input_tokens、completion_tokens→output_tokens、prompt_tokens_details.cached_tokens→cache_read_input_tokens；缓存写字段仅在官方 OpenAI 缓存契约（prompt_cache_key 按会话限定）下上报。
  • 图与代码的合并说明：实际代码中「同构累加」与「组装最终消息」发生在同一个 for-await 循环内（message_stop 分支触发组装），图中拆为两步以便阅读；「复做共享预处理」里 claude.ts 主干已做过一遍规范化，适配层对收到的 messages 再跑一次 normalizeMessagesForAPI 并重做延迟工具过滤（claude.ts:1345-1347 注释：OpenAI 需要全量工具池供 SearchExtraToolsTool 检索被过滤的 MCP 工具）。
