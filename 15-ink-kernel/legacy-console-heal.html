Windows 老控制台 legacy 自愈流播放器：启动检测 → 每帧 gate → 周期性全量重绘

没有 ConPTY 的老 Windows（build 低于 17763）上，conhost 处理增量刷新会漂。claude-code 的对策是两道防线：渲染宽度缩一列（绕开 pending-wrap bug 的触发条件）+ 每约 1 秒一次全量重绘替换增量 diff（把积累的残影一次清零）——「短暂劣化换长期正确」。

完整 · legacyConsole 模块缓存cachedMode='periodic' / 1000ms 的检测与配置不受影响——问题出在门之后的执行，不在检测
部分 · LogUpdate 内部状态gate 每帧照常判「到期」，但替换不再落笔——lastLegacyReset 不再前进，计时器卡死在到点状态
缺失 · 终端屏幕增量 diff 继续落屏：漂移与残影持续积累，永远等不到那次整屏重写——屏幕不再自愈
另一种「断」与它无关的兜底：resize / 视口收缩触发 reason 'resize' 的全量重置——先于 legacy 门判定，永远可用
恢复 / 兜底路径
  • 拖一下终端窗口：resize → 无条件 fullResetSequence('resize')（log-update.ts:150-155，先于 legacy 门）→ 立即整屏重画
  • 重启进程：模块缓存重建；prev 是空屏 → 首帧 diff 天然全量打底
  • 坏得快的机器：设 CLAUDE_CODE_LEGACY_CONSOLE=2（always）每帧全量重绘，重启后生效
两道防线为什么是「缩一列 + 周期重绘」
  • 防线① 渲染宽度缩一列：effectiveColumns = cols−1，满宽行永不触碰最后一列 → pending-wrap（写最后一列立即换行、物理光标多走一行）的触发条件被绕开——增量 diff 和全量重绘都不再因它多漂。
  • 防线② 周期性全量重绘：每 ~1000ms 用「clearTerminal + 从 (0,0) 起整屏重写」替换本帧的增量 diff，把窗口期内积累的残影/错位一次清零。
三种模式CLAUDE_CODE_LEGACY_CONSOLE
  • periodic（win32 且 build 低于 17763 时自动）：每 interval 全量一次。
  • always（=2）：每帧全量——给「每个增量 diff 都立刻花屏」的机器；最大闪烁、最大正确。
  • off（=0，或非 win32 / build ≥ 17763）：gate 关闭，此路径完全不存在。
边界与代价
  • RESET_MS 被 clamp 到 [100,10000]，防误配置。
  • 每次全量重绘 = 一次闪烁：reason 'clear' 计入 flicker 事件，两次闪烁间隔 < 1 秒（连发）才上报 tengu_flicker；reason 'resize' 的闪烁跳过上报；支持 DEC 2026 原子输出的终端整体跳过。窗口变窄/变宽也触发全量（reason 'resize'），共用同一条 fullResetSequence。
  • 考据分歧：子系统档案把 flicker 上报描述为「1 秒去重」，与实码相反（interactiveHelpers.tsx:356 是 间隔 < 1000 才上报，即连发检测）；本页以实码为准。
  • 强制 =1 跑在现代终端上：白损一列宽（缩列与 gate 同门控制）。
