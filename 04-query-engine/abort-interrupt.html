用户打断（abort）：ESC → 信号传播 → 合成 tool_result → 终止

claude-code · 04-query-engine 子系统 · 可播放动态流程图 · 配套同目录 architecture.html（静态架构图）

一次打断不是一个「异常」，而是一条和正常回合同样严谨的收束链路：用户按 ESC → 一棵 AbortController 树级联断电（在飞的 HTTP 流 / 工具子进程同时被切断）→ 被打断的工具盖上合成 tool_result 保证配对完整 → 注入打断消息 → query() 返回 Terminal（aborted_streaming / aborted_tools）→ finally 把队列命令按「已取消」结算。之后会话照常可继续。

⚡ AbortController 树 打断信号父 → 子级联
一棵控制器树：REPL / QueryEngine 持根，工具执行器持子代（sibling），每个工具再持孙代。父 abort 级联到子，子不反向影响父（WeakRef 弱引用传播，不妨碍 GC）。
☁ API 流式请求 SSE在飞的 HTTP 流

打断之后留下了什么（现场清单）
  • 保留、不回滚：半截 assistant 回答（onCancel 先存成消息）、已完成的 tool_result、打断消息、合成 tool_result —— 全部进入会话历史；消费者已收到的部分消息不删除。
  • 必须补齐：每个孤儿 tool_use 一条合成 tool_result（is_error=true）。漏掉的话，下次请求会因 tool_use / tool_result 配对不完整被 API 400 拒绝。
  • 结算语义：Terminal aborted_streaming / aborted_tools 在 getAutonomyTurnOutcome 中映射为 cancelled（不是 failed）—— 队列里的 autonomy 命令按「已取消」结算并回队；langfuse trace 标记 interrupted。
  • 下一回合前：REPL 天然每回合新建 AbortController；QueryEngine 必须显式 resetAbortController()，否则下一条 submitMessage 一提交就立刻被打断。
  • 三种打断形态：ESC（reason='user-cancel'，注入打断消息）；提交型（reason='interrupt'，不注入 —— 队列里的新用户消息本身就是上下文，且只有 interruptBehavior=cancel 的工具被取消）；SDK 侧 QueryEngine.interrupt()（不带 reason，会注入打断消息）。
证据与考据（源码实读）
  • ESC 路由：Ink keybinding chat:cancel → CancelRequestHandler → REPL.tsx:2547 onCancel()。onCancel 顺序：救 UI（2600-2606 把半截 streamingText 存成 assistant 消息；2608 resetLoadingState）→ 2631 abortController.abort('user-cancel') → 2638 setAbortController(null)（防后续 ESC 撞上已 abort 的旧信号）。tool-permission 对话框分支改走 toolUseConfirmQueue[0].onAbort()；remote 分支走 cancelRequest()。
  • 控制器级联：utils/abortController.ts:68-99 createChildAbortController —— WeakRef 单向父→子传播（30-36 propagateAbort），子 abort 不影响父。StreamingToolExecutor 构造时持子代 siblingAbortController（StreamingToolExecutor.ts:58-61）；每个工具再持孙代 toolAbortController（:328-330，Bash spawn 监听该信号）；孙代 abort 会向上冒泡到 query 控制器（:331-345，权限对话框拒绝场景）。
  • 合成 tool_result：StreamingToolExecutor.ts:180-199 createSyntheticErrorMessage('user_interrupted') —— 内容为 REJECT_MESSAGE（utils/messages.ts:213「用户不想继续此工具调用……」），is_error=true，带 tool_use_id。取消判定 :237-258 getAbortReason：reason='interrupt' 时只取消 interruptBehavior=cancel 的工具（:246-255）。
  • 两个检查点：流式阶段 query.ts:1302-1339（有执行器 → getRemainingResults 收合成结果；无执行器 → yieldMissingToolResultBlocks 为孤儿 tool_use 补「Interrupted by user」，:149-179）；工具阶段 query.ts:1779-1810（同样补齐 + maxTurns 检查 1800-1808）。两处都遵循「reason !== 'interrupt' 才注入打断消息」（:1333 / :1795），打断消息文案见 messages.ts:208-210。
  • API 层：signal 经 query.ts:904 下发；SDK 抛 APIUserAbortError 后，内层 claude.ts:2553-2581 区分真用户打断（signal.aborted=true → 原样上抛）与 SDK 超时（转 APIConnectionTimeoutError）；外层 catch claude.ts:2924-2927 对 APIUserAbortError 静默 return（不产错误消息，打断消息由 query.ts 负责）。
  • finally 收尾：query.ts:329-381 —— finalizeAutonomyCommandsForTurn（outcome 经 getAutonomyTurnOutcome :211-236 映射，aborted_* → cancelled）后回队；endTrace 标记 interrupted + flush；闭包链 langfuse 引用置 null 促 GC。
  • 提交型打断：handlePromptSubmit.ts:323-341（queryGuard 活跃且有可打断工具时 abort('interrupt') 并把新消息入队）；REPL 队列 'now' 优先级消息同样 abort('interrupt')（REPL.tsx:5202-5208）；无头路径 print.ts:1911。QueryEngine 侧：QueryEngine.ts:1217-1225 interrupt() / resetAbortController()（构造器 :211 建初始控制器）。
  • 考据注记：chicago MCP 清理在两个检查点都会尝试（query.ts:1320-1329 / 1783-1792，CHICAGO_MCP feature 门控、主线程限定、失败静默）—— 本图省略；onCancel 中 mrOnTurnComplete 以 aborted=true 直接触发（REPL.tsx:2641，绕过 forceEnd 跳过的 finally 路径）；AbortSignal 树的存在使「打断」成为原子单元——信号全局可见、无竞态窗口。
