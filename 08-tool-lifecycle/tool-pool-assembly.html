工具池组装流

组件 08-tool-lifecycle · 工具生命周期

从「settings 里的权限规则」到「模型这一回合能看到哪些工具」之间发生的全部事情：规则加载 → 权限上下文组装 → 条件收集内置工具 → deny 剥离与模式裁剪 → 与 MCP 工具合并去重排序 → 延迟工具剔除 → 随 API 请求发出；规则或 MCP 变化时整条链重新组装。

处理步骤 判定分支 分支去向 开始 / 结束 旁注机制 灰色小字 = 对应源码模块（仅作定位锚点）· 左侧长回边 = 重新组装循环
深入细节（证据与考据）
  • 证据来源：src/utils/permissions/permissionsLoader.ts（loadAllPermissionRulesFromDisk:120-146，五处来源循环加载）、src/tools.ts（getAllBaseTools:218-284、getTools:304-360、filterToolsByDenyRules:295-302、assembleToolPool:378-400）、src/services/mcp/client.ts（fetchToolsForClient:1755-1844）、src/hooks/useMergedTools.ts、src/screens/REPL.tsx:1079、src/services/api/claude.ts:1151-1204。
  • 规则来源：userSettings/projectSettings/localSettings/flagSettings/policySettings 五处 settings 文件循环加载；allowManagedPermissionRulesOnly 开启时只取 policySettings。权限上下文持有 allow/deny/ask 三类规则与权限模式，deny 剥离用的是与运行时权限判定相同的匹配器（step 1a）。
  • getTools 内部顺序与图中略有合并：先移除三个特殊工具（ListMcpResources/ReadMcpResource/StructuredOutput），再 deny 剥离，再 REPL 模式隐藏 REPL_ONLY_TOOLS，最后 isEnabled 自检；CLAUDE_CODE_SIMPLE=1 在最前直接返回 Bash/Read/Edit 三件套（协调模式补 Agent/TaskStop/SendMessage）。assembleToolPool 对 MCP 工具会再过一次同样的 deny 匹配器（图 D1 分支同时覆盖这两处）。
  • 排序细节：内置与 MCP 各自 localeCompare 排序后拼接（内置在前），uniqBy 按名去重保留先插入的内置工具——源码注释明确服务端 claude_code_system_cache_policy 在最后一个前缀匹配的内置工具后放全局缓存断点，混排会让下游所有缓存键失效。
  • 延迟工具剔除（claude.ts:1187-1204）：启用搜索时延迟工具永不进入 tools 数组（连已发现的也不把 schema 加回，由 ExecuteExtraTool 运行时查全局注册表调用，保持 tools 数组稳定以保 prompt cache）；未启用时反而把 SearchExtraTools 自身从池中移除。启用判定 isSearchExtraToolsEnabled 受模式/模型/阈值三重门控（无延迟工具且无待连服务器时自动关闭）。
  • 重组装触发：每次 query、规则或 MCP 连接变化时整条链重跑；useMergedTools 是 useMemo（依赖 initialTools/mcpTools/toolPermissionContext），查询中途 MCP 接入靠 refreshTools 换新 toolUseContext.options.tools。工具搜索门控若在会话中途翻转，已见过的工具会从请求中消失（可见性突变，源码 failure mode 注记）。
  • 考据注记（来自子系统考据 tools-permissions.json）：CORE_TOOLS 数量存在文档漂移（CLAUDE.md 称 38，实测 29）；Tool.shouldDefer 字段无运行时消费者，延迟判定实际只看 alwaysLoad 与 CORE_TOOLS——直接影响本流程「剔除延迟工具」一节的语义。
