组件架构：文件改动检查点

24-file-history · 组成模块与调用关系

「AI 改过的文件，能不能退回到某条消息时的样子」由这套检查点回答：编辑工具动文件前先把老内容存底，每条用户消息之后再拍一轮快照；反悔时按消息把文件现场退回去，换会话恢复时把备份搬进新家。三处落点：磁盘备份仓库、会话日志里的快照条目、内存里的快照索引。

组成模块（实线箭头 = 调用/控制流） 分支路径（回滚与恢复迁移：把检查点用起来） 外部组件 / 调用方（标「组件 NN」） 共享底座（磁盘备份仓库与会话身份） 灰色小字 = 源码模块锚点（仅定位用，非图面内容）
深入细节（证据与考据）
  • 证据来源（已抽查核对）：核心 src/utils/fileHistory.ts:88-195（trackEdit 三相提交：捕获→异步备份→重检回写；99-120 查重防止覆盖确定性 {hash}@v1 备份）、:200-344（makeSnapshot：逐追踪文件 stat/mtime 检查后增量备份，删除文件记 null 标记 :243-255）、:349-399（rewind，按 messageId 定位快照，找不到即抛错）、:539-593（applySnapshot：null 备份＝删除该文件，restoreBackup 恢复内容与权限）、:416-486（getDiffStats 差异预览）、:727-743（备份名＝路径 sha256 前 16 位@vN；resolveBackupPath＝{配置目录}/file-history/{会话ID}/）、:750-800（copyFile 落盘、惰性 mkdir、chmod 保留权限）、:890-919（fileHistoryRestoreStateFromLog 重建索引）、:924-1048（copyFileHistoryForResume：硬链接、EEXIST 跳过、失败回退 copyFile、整快照失败则不记条目）。
  • 调用方（已抽查核对）：编辑前备份由 FileEditTool.ts:427-431、FileWriteTool.ts:256-260、NotebookEditTool.ts:313-314、BashTool.tsx:529-530（内嵌 sed 写文件前）调用；每轮快照由 QueryEngine.ts:653-668（引擎路径，过滤可选中用户消息）与 handlePromptSubmit.ts:556-566（界面提交路径）调用，REPL.tsx:3911 初始消息也拍一份；回滚入口三处：REPL.tsx:6539-6553（消息选择器「恢复代码」→ fileHistoryRewind）、cli/print.ts:749-783（--rewind-files：须配 --resume、仅限用户消息 UUID、回滚后立即退出）、print.ts:3204-3216（SDK 控制请求 rewind_files，支持 dry_run 只预览）；界面判定由 MessageSelector.tsx:82-122 用 fileHistoryCanRestore/getDiffStats 驱动。
  • 记账与恢复：快照条目经 sessionStorage.ts:1108-1122（insertFileHistorySnapshot）与 :1513-1519（recordFileHistorySnapshot，trackEdit 补录与 makeSnapshot 新增都调用）混排进会话 JSONL；加载时 buildFileHistorySnapshotChain（:2287-2311）按消息序合并、后写的覆盖先写的；恢复链路 conversationRecovery.ts:570-604（copyFileHistoryForResume + 快照清单随结果返回）、sessionRestore.ts:104-106（SDK 侧 restoreStateFromLog 回填 AppState）、hooks/useFileHistorySnapshotInit.ts（界面挂载时一次性重建）；AppState 字段见 AppStateStore.ts:225/514-517。
  • 考据注记（合并与省略）：本组件在源码中是单个 fileHistory.ts（约 1100 行），图中按职能拆为五个模块盒子；「快照条目记账」的实际写函数 recordFileHistorySnapshot 属组件 22 的 sessionStorage.ts，图上画成指向组件 22 的虚线；trackEdit 与 makeSnapshot 都写条目、都更新内存索引，图面各只画了一条代表箭头（B1→日志、B2→索引），未画 B1→索引与 B2→日志，以免箭头交叉；恢复迁移对索引的重建（SDK 走 sessionRestore、界面走挂载钩子）并入迁移盒子文字，未单独画箭头。MAX_SNAPSHOTS=20（fileHistory.ts:54-56，注释自述「检查点导致内存无限增长，改增量 diff 前不再调大」）只淘汰内存列表，磁盘备份文件不删。
  • 门控开关：交互会话默认开启（globalConfig.fileCheckpointingEnabled ≠ false 且环境变量未禁用，fileHistory.ts:65-73）；SDK / 无界面会话默认关闭，须 CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING 显式打开（:75-80）；makeSnapshot 的 VS Code 文件变更通知（notifyVscodeSnapshotFilesUpdated，:1056-1100）为 fire-and-forget 副作用，未上图。
  • 考据分歧：fileHistory.ts:48-51 注释称 snapshotSequence 计数「供 useGitDiffStats 用作活跃信号」，但全仓检索未见 useGitDiffStats 实际消费该字段，/clear 与恢复路径只将其归零（conversation.ts:215、main.tsx:3552）——疑为陈旧注释；磁盘仓库路径由 envUtils.getClaudeConfigHomeDir() 决定，默认 ~/.claude/。
  • 与其他图的关系：会话日志文件本身的写入队列与退出冲刷见组件 22；恢复的完整编排（多源定位、换脑、成本恢复）见组件 23；编辑工具的执行流见组件 08/11。
