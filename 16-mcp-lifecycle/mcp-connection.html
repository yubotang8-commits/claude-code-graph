MCP 服务器连接生命周期

组件 16-mcp-lifecycle · MCP / Hooks / 技能与命令

从「REPL 挂载连接管理器」到「远程工具进入模型工具池」：配置聚合 → 分批并发连接 → 握手竞速 → 四类清单拉取 → 批量写回 → 长驻监听。每台服务器独立成败，一台失败不拖累其他。

深入细节（证据与考据）
  • 证据来源：src/services/mcp/useManageMCPConnections.ts（挂载、16ms 批量写回、onclose 重连、list_changed 刷新）、src/services/mcp/config.ts（scope 合并与企业独占）、src/services/mcp/client.ts（transport 创建、连接超时竞速、四类清单拉取、本地/远程分批）、src/skills/mcpSkills.ts、src/hooks/useMergedTools.ts、src/tools.ts、src/hooks/useMergedCommands.ts、src/screens/REPL.tsx（MCPConnectionManager 挂载与工具合并）。
  • 考据注记：实际链路 9 个站点，本图展开为 14 个主干节点；enterprise MCP 配置存在时独占全部服务器（其他 scope 全被忽略），图中以「企业配置独占」一行带过；.mcp.json 项目级配置需用户批准后才参与合并。
  • 禁用判定在代码中出现于三处而非一处：预写 pending 时（isMcpServerDisabled 直接把占位写成 disabled，useManageMCPConnections.ts:815-817）、发起连接前过滤 enabledConfigs（:885-887）、批处理入口再分区一次（client.ts:2253-2266）——本图合并为一个判定节点，置于分批之前以匹配首次判定位置。
  • 同一套装配逻辑也服务无头模式：print（-p）模式每台服务器连接完成后增量写入 headlessStore.mcp，最终同样经 assembleToolPool 组装工具池（cli/print.ts:1503 附近 buildAllTools），与 REPL 的 useMergedTools 共享这个纯函数。
  • 三种非成功落态（禁用 / 需登录 / 失败）与成功态走同一条 updateServer 批量写回通道：失败或禁用时该服务器的 tools/commands/resources 自动清空（useManageMCPConnections.ts:232-243），需登录时替换为一个 McpAuthTool 登录引导工具——这就是右下汇合点的含义。
  • 资源浏览工具（ListMcpResources / ReadMcpResource）只在第一个声明支持 resources 的服务器落态时挂载一次（client.ts:2372-2376），本图并入「并发拉取四类清单」节点。
  • 自动重连只覆盖远程传输（SSE/HTTP 等）：指数退避 1s→30s、至多 5 次（useManageMCPConnections.ts:88-90, 371-464）；stdio/SDK 断线直接落 failed，等 /mcp 手动重连。list_changed 通知只重拉该服务器自己的清单并作废对应缓存。
  • claude.ai 连接器是第二阶段：与本地配置的连接并行发起拉取，配置到货后再补一批连接（useManageMCPConnections.ts:852-958 两阶段 effect）。
  • packages/mcp-client 是完整的 MCP 协议客户端库，但主 CLI 运行时只从它导入 3 个符号（client.ts:123-127），连接逻辑在 src/services/mcp/client.ts（3400+ 行）里另行实现了一遍——反编译产物的双轨并存，未确证 createMcpManager 有外部消费者。
  • KAIROS channel 推送、elicitation 请求队列、401 缓存跳连（15 分钟 TTL）等门控机制本图省略。
